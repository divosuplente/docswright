# docswright

A CLI that generates Markdown documentation sites: Antora-style aggregation
from multiple sources and versions, plus an Azure DevOps-style wiki you can
edit in the browser and publish to Azure DevOps.

docswright is an executable, not an app. It scaffolds a standalone project (its own
`package.json` and Astro+Starlight site) and then drives that project.

## Install

```sh
npm install -g docswright         # global command
npx docswright new site my-docs   # or use without installing
```

Installs two equivalent commands: `docswright` and the short `dw`.

Node >= 20.19. A project does not need `typescript` or `tsx`: the CLI ships as
TypeScript and loads its own sources and your `docswright.config.ts` at runtime.

## Quickstart

```sh
docswright new site my-docs     # or: dw new site my-docs
cd my-docs
npm install
npm run build                   # sync sources, build the static site
npm run wiki                    # serve on http://localhost:4000 with the editor
```

Open <http://localhost:4000> for the site and
<http://localhost:4000/_admin/> for the wiki editor.

Commands, run from inside a project:

```sh
docswright sync                 # fetch + sync content only (no site build)
docswright build                # sync, then build the static site
docswright wiki [--port 4010]   # serve the built site plus /_admin/
docswright publish --org … --project … --wiki …   # push wiki pages to Azure DevOps
```

Node is required regardless: the generated output is an Astro+Starlight site,
so Python would only add a second runtime to drive the same toolchain.

## Configuring sources

`docswright.config.ts` (in the project root) is the playbook equivalent:

```ts
export default {
  siteTitle: 'docswright Docs',
  components: [
    {
      name: 'demo-docs',
      versions: [{ label: 'current', source: { type: 'local', path: 'demo-docs' } }],
    },
    {
      name: 'other-docs',
      versions: [{
        label: 'v1.0',
        source: { type: 'git', url: 'https://host/repo.git', ref: 'v1.0', dir: 'docs' },
      }],
    },
  ],
};
```

- `name` — slug-safe component name, the first URL segment
- `versions[].label` — second URL segment (`/component/version/page/`)
- `local` sources copy the given directory; `git` sources are cloned
  (`--depth 1`, reusing your local git credentials) into `.docswright/cache/`
  and refreshed with fetch + reset on later syncs
- `dir` optionally narrows a source to a subdirectory

Sync rewrites `src/content/docs/<component>/<version>/` from scratch, adds a
`title` frontmatter key when missing (from the first `# H1`, else the
filename), and removes the duplicated leading `# H1` so the title is not
rendered twice. Existing other frontmatter is preserved. Markdown links
between pages are ordinary filesystem-style links, e.g.
`[Getting Started](/demo-docs/current/getting-started/)`.

The site landing page lives at `src/content/docs/index.md`. `sync` never
overwrites it, and recreates a default splash page if it is missing, so
wiping `src/content/docs` is safe. The sidebar is autogenerated as
component → version → pages.

## Project layout

`docswright new` writes a standalone project; the engine is not vendored into it.
Every command resolves the project root by walking up from the current
directory until it finds `docswright.config.ts`, so `docswright` works the same in a
freshly generated project, a linked install, or a global one.

## Wiki editing

Wiki pages are docswright markdown files in `wiki/`. The admin UI at `/_admin/`
lists them, and lets you create, edit, rename and delete pages. Every change
triggers one background rebuild (sync + astro build, single-flight), after
which the site serves the updated page.

Admin HTTP API (used by the UI):

```
GET    /_admin/api/tree
GET    /_admin/api/pages?path=PAGE
POST   /_admin/api/pages           {path, content}
PUT    /_admin/api/pages           {path, content}
POST   /_admin/api/pages/move      {from, to}
DELETE /_admin/api/pages?path=PAGE
GET    /_admin/api/rebuild         → {running, lastStatus, lastError?}
POST   /_admin/api/rebuild
```

## Publishing the wiki to Azure DevOps

```sh
pnpm wiki:publish --org https://dev.azure.com/yourorg \
  --project 'My Project' --wiki OurWiki [--create] [--dry-run]
```

Uses your existing Azure CLI login (`az login`) to mint an ADO token — no
`azure-devops` extension required. Every `wiki/**/*.md` page is upserted by
path via the wiki REST API (`If-Match: *`), so re-runs update in place and
folders in `wiki/` become wiki subpages. `--create` creates a project wiki
when it does not exist; `--dry-run` prints the plan without calling ADO.
Only pages are pushed — it never deletes remote pages that are absent
locally.

## Limitations (v1)

- No authentication: the wiki server binds `127.0.0.1` only.
- Rebuilds are full site builds; edits are live after a few seconds, and
  `dist/` is briefly updated in place while rebuilding.
- Renaming a page does not rewrite links pointing at it.
- Last write wins; no edit-conflict detection.
- Publishing is upsert-only: pages deleted locally stay in the remote wiki.
